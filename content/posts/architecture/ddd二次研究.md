# 概念
领域：业务范围 业务相关知识的集合  
子域：领域的拆分,单个子域实际可以由多个限界上下文表示，领域是对问题空间的划分，界限上下文是对解空间的划分，问题空间映射到解空间的方式决定了领域和界限上下文之间的对应关系。    
限界上下文：定义领域边界，以确保每个上下文含义在它特定的边界内都具有唯一含义,比如电商有订单的概念，物流也有订单，战术设计是在某个上下文内进行 帮助我们进行业务拆解，和边界划分。  
通用语言：在限界上下文含义唯一 帮助我们理解业务概念是什么，能干什么    
上下文映射图：多个限界上下文之间交互  
微服务: 一个限界上下文理论上就可以设计为一个微服务，一个微服务也可以包含多个bc 
模块：模型中的模块表示了一个命名的容器，用于存放领域中内聚在一起的类  
com.hzmc.限界上下文.domian.model.user  
com.hzmc.限界上下文.domian.model.role  
问题空间和解空间：分为构成描述需求问题的真实世界与获取解决方案的理念世界。整个软件构建的过程，就是从真实世界映射到理念世界的过程  
问题空间：对问题空间进行合理分解，识别出核心子领域、通用子领域和支撑子领域，并确定各个子领域的目标、边界和建模策略。  
解空间：对问题空间进行解决方案的架构映射，通过划分限界上下文，为统一语言提供知识语境，并在其边界内维护领域模型的统一。每个限界上下文的内部有着自己的架构，限界上下文之间的协作关系则通过上下文映射来体现和表达。方法
领域事件：用特定方式（已发生的时态）表达发生在问题域中的重要事情 在用户注册过程中，我们可能会说“当用户注册成功之后，发送一封欢迎邮件给客户。”，此时的“用户已经注册”便是一个领域事件。  
事件风暴：以领域事件为线索逐步得到领域模型，通过领域事件识别出聚合根，进而划分微服务的限界上下文。在活动中，团队先通过头脑风暴的形式罗列出领域中所有的领域事件，整合之后形成最终的领域事件集合，然后对于每一个事件，标注出导致该事件的命令（Command），再然后为每个事件标注出命令发起方的角色，命令可以是用户发起，也可以是第三方系统调用或者是定时器触发等。最后对事件进行分类整理出聚合根以及限界上下文  
四色建模法：
分层架构
用户接口层: rest rpc等各种协议接口, 接收vo， dto等对象。浏览器 controller。  
应用层：门面, 暴露接口, 编排，调用工厂获取实体，调用领域服务，接收dto对象。  
领域层:承载具体业务，包含领域服务 实体 值对象 聚合 工厂这些。  
工厂：新增的时候创建对象，简单的拷贝或者生成自增id，不涉及业务，涉及业务，如计算优惠价格放到实体。  
领域服务：分担实体的功能，承接部分业务逻辑，做一些实体不变处理的业务流程,它不是必须的，比如加密。也可以作为工厂调用防腐层的转换功能。  
实体：有一对象拥有唯一标识，两个实体的标识是否一样代表相同,以Entity结尾。怎么持久化，3种方式。唯一标识生成的方式。  
值对象:无唯一标识的简单对象 ，判断两个值对象相等的标准是判断他们的每个属性是否有相同的值。重写equal方法要注意。以ValueObject结尾。值对象是不变的。怎么持久化。  
聚合: 包裹多个实体，单个实体无法完成某个业务，比如订单明细，明细是和主单一起，主订单是聚合根，聚合多大，有点不方便的是需要查询明细也必须查询获取聚合根，包含了主单，造成了资源浪费, 所以demo里面是根据情况来的。建议在一个事务中只修改一个聚合实例。  
聚合之间的引用。  
聚合根：比如主单就是聚合根。  
基础设施层：一些增删改查操作，屏蔽的底层细节。这里应该接收entity 转成po, 和传统的dao接口不是一个概念。原则上该层只有save. delete query等方法，但是考虑到实际情况，可以有updateName方法，不然有更新覆盖的可能。  
六边形模式：主适配器 从适配器   业务逻辑、技术实现进行分离  
防腐层：多个限界上下文集成 用来集成多个限界上下文  
其他还有共享内核  
开放主机服务:将开放主机服务看成是远程过程调用的API  
cqrs:指读取和写入分别拥有单独的数据结构   视图需要跨聚合根，列很多(很少)，怎么办？  
贫血模式 业务代码和模型分离 业务代码散落在各个service 难以维护  
领域事件：用特定方式（已发生的时态）表达发生在问题域中的重要事情 在用户注册过程中，我们可能会说“当用户注册成功之后，发送一封欢迎邮件给客户。”，此时的“用户已经注册”便是一个领域事件。

# 落地细节
Repository并不与某种持久化机制绑定，一个被抽象出来的Repository向外暴露的功能“接口”始终是向领域模型提供聚合根对象 控制反转  
聚合根一定是实体对象，但是并不是所有实体对象都是聚合根，同时聚合根还可以拥有其他子实体对象。聚合根的ID在整个软件系统中全局唯一，而其下的子实体对象的ID只需在单个聚合根下唯一即可  
创建聚合根通常通过设计模式中的工厂(Factory)模式完成  
聚合根是业务逻辑的主要载体，也就是说业务逻辑的实现代码应该尽量地放在聚合根或者聚合根的边界之内。但有些业务逻辑并不适合于放在聚合根上，在这种的情况下，我们引入领域服务。比如生成工单号的逻辑。将聚合根作为入参。  
应用层入参command对象, Command对象只是一种类型的DTO对象，它封装了客户端发过来的请求数据。  
读模式  
先使用资源库获取聚合根, 然后调用领域服务转成对应的vo.  
直接使用sql,不使用资源库，领域服务直接查询，不借助领域模型。微软也提倡过这种方式  
https://docs.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/apply-simplified-microservice-cqrs-ddd-patterns  
cqrs CQRS中查询服务不会调用应用服务，也不会调用领域模型和资源库Repository，它会直接查询数据库或者ES获取原始数据对象DO  
不是属于单个聚合根的业务或者需要多个聚合根配合的业务，放在领域服务中，注意是业务，如果没有业务，协调工作应该放到应用服务中  
静态方法放在领域服务中  
需要通过rpc等其它外部服务处理业务的，放在领域服务中  
MQ、Event、Cache的实现都应该在基础设施层  
防腐层Adapter应该放在基础设施层, 可以在Adapter中再创建一个Translator实现上下文模型之间的翻译功能

# ddd落地的难点
业务划分不规范  导致需要额外维护实体
系统间耦合 互相知道不应该知道的东西 导致需要传不需要传的对象
业务逻辑本身有问题 代码如何设计的没问题
实体和持久化po 需要分开吗
BaseOldResponse request 只能在controller层
utils充斥业务代码
大段的try catch
代码的不合理来自业务逻辑的不合理
